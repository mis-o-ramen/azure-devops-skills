# 設計 — アイデアを作業アイテムに落とす

人間の粗いアイデアを起点に、対話と調査を経て、実装に着手できる作業アイテムを作るまでの
手順。出力は実装工程（兄弟スキル `issue-implement`）の入力になる。あちらの手順 3 が
「受け入れ基準が空なら止まる」「推測で実装しない」と定めている以上、ここで作る作業
アイテムは、実装する人が質問せずにテストと実装を書けるところまで埋まっていなければ
意味がない。

## この段の入口

入口条件: **解決したいことはあるが、受け入れ基準の埋まった作業アイテムが無い**
（ループの定義は `../azure-devops/references/loop.md`）。条件が違う依頼は該当する段に渡す。

- 受け入れ基準の埋まった作業アイテムが既にあり、実装を求められている → `issue-implement`
- プルリクエストのレビュー → `ado-review`、プルリクエストへの指摘の対応 → `ado-fix`

起点はチャットの依頼でも、粗く起票済みの作業アイテムでもよい。作業アイテムが起点なら
`wit get` と `wit comments` で読んでから始める。起票前の設計メモにレビューの指摘が付いて
戻ってきたときもこの段で、「レビュー指摘を受けたら」から入る。

## 能力層

Azure DevOps の操作（`wit …` / `pr …` / `build …`）はすべて兄弟スキル `azure-devops` の
`scripts/ado.py` を通す。コマンドの一覧・セットアップ・フィールドの調べ方は
`../azure-devops/SKILL.md`。兄弟配置（同じ skills ディレクトリ直下）が前提。

## 出力規約

書き方は `../azure-devops/references/writing.md`。この手順固有の上限は次の 5 つ。

- 人間への質問は 1 回にまとめて最大 5 件、1 件 1 行。小出しにしない。溢れた分は、覆すと
  手戻りが大きいものを先にして次の往復に回す
- 仕様を決める質問には推奨と根拠（`path:line` か作業アイテム ID）を付ける。選択肢だけを
  並べて「どうしますか」と返さない。推奨を出せないときは、何が分からないから出せないのかを
  書く
- 方針の選択肢は最大 3 案。1 案 1 行の比較に収め、推奨に印をつける
- 設計判断として作業アイテムに書くのは最大 3 件。**覆すと手戻りになるものだけ**
- 受け入れ基準が 8 件を超えたら、基準を削るのではなく作業アイテムの分割を疑う。
  境界・異常系の基準は削る対象にしない

## 自分で決めることと、人間に聞くこと

作業アイテムに書かれなかった仕様は消えない。実装の段で止まるか、実装者の推測で埋まるか、
レビューで「未定義」の指摘になる。どれも設計の段で埋めるより高くつく。だから埋める。
誰が埋めるかは次の線で分ける。

- **自分で決める** — 手順 1 の「委ねられていること」に入るもの。既存コードの振る舞いに
  揃える、同種の既存機能に合わせる、で決まるものが大半を占める。決めたことは根拠を添えて
  手順 7 の承認で示し、人間はそこで覆せる
- **人間に聞く** — 「解決したいこと」「決まっていること」に触れるもの、委ねられた範囲の
  外にあるもの、コードからは決まらない業務上の判断（誰に何を許すか、データをいつ消すか）。
  出力規約の形で、推奨を付けて聞く

決めていない事項を見つけたら、聞く前にこの線で分ける。委ねられた範囲のものを質問にすると、
調査の仕事が人間に移るだけになる。

## 手順

### 1. 解決したいことを聞き取る

アイデアは「何を作るか」の形で来ることが多い。実装に落とす前に「何を解決するか」に
引き直す。作るものが同じでも、解決したいことが違えば受け入れ基準が変わる。

次の 3 つを依頼者との対話で確認する。

- **何を解決するか** — 今、誰が、何に困っているか。今はどう凌いでいるか
- **決まっていること** — 依頼者の中で確定していて、覆してはいけないこと
- **委ねられていること** — こちらの調査と提案で決めてよいこと

答えが本文から読み取れるなら聞かない。曖昧な点だけを質問にして、まとめて 1 往復で
確認する。解決したいことが確認できないまま先へ進まない。作り方の議論は解決したい
ことが定まってからで、逆順にすると選択肢の比較軸が作れない。

「委ねられていること」は後の手順で自分が決めてよい範囲の線になる。依頼者が明言しない
ときは「既存の振る舞いに揃える範囲はこちらで決め、承認時に一覧で示す」と伝えて確認する。

### 2. 既存を調べる

コードベースの読解を主にする。ネットワークが社内に閉じている場合、外部の検索や取得は
使えない。到達できない情報源を前提にした計画を立てない。

- 同じ課題を扱った作業アイテムが既に無いか `wit query` で探す（WIQL は
  `../azure-devops/references/recipes.md`）。重複や過去の見送りが見つかれば、それ自体が
  判断材料になる
- 実現方法の候補を、既存コードのどこに乗るかまで特定する。ファイルを開かずに挙げた
  候補は選択肢ではなく想像で、選ばれた後で覆る

### 3. 方針の選択肢を出し、人間が選ぶ

調査で得た選択肢を最大 3 案、1 案 1 行の「案 — 利点 / 欠点」で並べ、推奨に印をつける。
覆すと手戻りになる懸念があれば 1 件 1 行で添える。

**選ぶのは人間。ここで止まり、選択を待つ。** 実質 1 案しかないときは選択肢の形を
やめ、その方針と根拠を示して異議がないかだけ確認する。

方針と一緒に、クラス名・関数名・画面文言といった実装の細部を出さない。それは実装
工程の裁量で、ここで固定すると判断材料が実装案の中に埋もれる。

### 4. 既存コードに当てて仕様を詰める

手順 3 の比較は「どこに乗るか」までしか見ていない。選んだ方針を、それが乗る既存コードに
当てて、決めていないことを洗い出す。ここを飛ばした本文は、実装やレビューで初めて読まれる
コードとぶつかって覆る。

1. 変更が入る箇所と、同じデータ・画面・API・設定を使う既存の利用箇所を特定する。
   参照元を辿り、ファイルを開いて読む。利用箇所の一覧は検討記録に `path` で残す
2. 次の観点ごとに、この変更で何が起きるかを決める

| 観点 | 問うこと |
| --- | --- |
| 入力と境界 | 空・0 件・上限・不正値・重複のとき何が起きるか |
| 状態 | 途中の状態、取り消し・やり直し、二重実行のとき何が起きるか |
| 失敗 | 依存先の失敗・途中までの成功・タイムアウトで、利用者に何が見え、データがどう残るか |
| 並行 | 同じ対象への同時操作で何が起きるか |
| データ | 既存データの扱い（移行・初期値）、削除と保持 |
| 権限 | 誰が、誰の何に対してできるか |
| 既存への影響 | 1 で特定した既存の利用箇所の振る舞いが変わるか。互換性 |
| 規模 | 件数・サイズ・頻度が既存の想定を超えるか |
| 運用 | 設定、ログ、切り戻し |

3. 観点ごとの結論を検討記録に 1 行で残す。形は `観点 — 結論 — 根拠 — 反映先`
   - 反映先は受け入れ基準の番号、スコープ外、設計判断のどれか。利用者に見える振る舞いを
     決めたなら受け入れ基準にする。決めた振る舞いが本文のどこにも無ければ、実装者には
     決まっていないのと同じ
   - 「該当なし」は、該当しない根拠（`path:line`）と一緒にだけ書ける。根拠の無い
     該当なしは、検討していないのと区別が付かない
   - 決まらないものは「自分で決めることと、人間に聞くこと」の線で分け、人間に聞くものを
     質問にまとめる

回答を得たら反映し、回答で変わった観点を当て直す。結論の無い観点を残したまま手順 5 に
進まない。

### 5. 作業アイテムの本文を書く

型ごとのフィールドは `wit describe-type` で確認する（`../azure-devops/SKILL.md` の
「最初にフィールドを調べる」）。書くのは次の 4 つ。

- **タイトル** — 解決することを書く。実現手段をタイトルにしない
- **説明** — 背景（なぜやるか）とスコープ外。手順 1 で確認した「解決したいこと」を
  ここに残す。実装する人が読むのは作業アイテムだけで、この対話は残らない
- **受け入れ基準** — 1 件 1 行、満たされたかを検証できる文で書く。正常系だけでなく、
  手順 4 で決めた境界・異常系の振る舞いも基準にする。`issue-implement` の手順 4 はこの
  1 件ごとにテストを割り振る。「〜できること」で終わる曖昧な文は割り振れず、そこで
  実装が止まる
- **設計判断** — 手順 3 で人間が選んだ方針と、覆すと手戻りになる決定だけ。最大 3 件

1 つの作業アイテムは、独立してレビューできる 1 本のプルリクエストで完了する粒度に
する。超えるならフィーチャーを親にして子ストーリーに分割し、子の間に実装順の依存が
あれば親の説明に 1 行で書く。

### 6. 自分でレビューする

依頼者に見せる前に、本文を別の読み手として読み直す。実装する人は作業アイテムだけを読み、
レビューする人は本文とコードを突き合わせる。この二人が出す問いを、ここで出し切る。

- 受け入れ基準 1 件ごとに、満たすために変わる箇所を `path` で言えるか。言えない基準は、
  どこに乗るかがまだ決まっていない
- 受け入れ基準 1 件ごとに、落ちるテストの前提・操作・期待が書けるか
- 本文の語が定義されているか。「適切に」「エラー時は」「必要に応じて」「など」のように、
  実装者に振る舞いを選ばせる語は未定義として扱う
- 基準同士、基準と「決まっていること」、基準とスコープ外が矛盾しないか
- 検討記録のすべての観点に結論と根拠があり、反映先が本文に実在するか

見つけた穴は手順 4 に戻って埋める。ここで見つけた穴は自分で埋められるが、レビューや
実装で見つかった穴は人間との往復を増やす。

### 7. 設計メモを示し、承認を得る

本文は起票まで設計メモ（Markdown ファイル）に置く。置き場所は依頼者の指定に従い、指定が
無ければ作業ディレクトリに置いてパスを報告する。設計メモの構成は次の 3 つ。

- **本文** — タイトル・説明・受け入れ基準・設計判断。起票される内容そのもの
- **自分で決めたこと** — 委ねられた範囲として自分で決めた事項。1 件 1 行、根拠付き
- **検討記録** — 手順 4 の既存の利用箇所と、観点ごとの結論。起票はせず、レビューの指摘に
  答えるときに引く

起票の前に設計メモを依頼者に見せて承認を得る。`html` 型フィールドは起票後に読んで書き
戻す修正ができないため（`../azure-devops/SKILL.md`）、本文は起票前に固めるのが安い。
本文の意味が変わらない反映（誤字、表記の統一、行の並べ替え）は、そのまま起票してよい。
受け入れ基準の追加・削除・文言の変更、タイトルの変更、スコープ外の追記は、反映した本文を
もう一度見せて承認を得る。軽微かどうかを自分で決めない。

### 8. 起票して報告する

```
wit create --type "User Story" --title "…" --description @body.md \
  --field-multiline Microsoft.VSTS.Common.AcceptanceCriteria=@criteria.md
wit create --type "User Story" --title "…" --parent <親id> …
```

分割した場合は親フィーチャーから先に作り、子は `--parent` でぶら下げる。起点が既存の
作業アイテムなら、そこに `wit comment` で起票した ID と URL を 1 行ずつ報告する。

`System.State` は触らない。いつ誰が状態を動かすかは組織の運用で決まっている。

## レビュー指摘を受けたら

起票前の設計メモを別のレビューにかけ、その指摘が戻ってきたときの手順。指摘の一覧を
そのまま人間への質問に変換して返さない。指摘に答えるのは、設計した側の仕事になる。

1. 指摘ごとに検討記録を引き、次の 2 つに分ける
   - **検討済み** — 記録に結論と根拠がある。指摘が根拠を崩していなければ、根拠を示して
     見送る。崩していれば検討漏れとして扱う
   - **検討漏れ** — 記録に無いか、根拠が無い。手順 4 と同じくコードを辿って結論を出し、
     「自分で決めることと、人間に聞くこと」の線で分ける
2. 検討漏れは症状として扱う。漏れた観点を本文全体に当て直し、同じ観点の他の漏れも埋める。
   指摘された 1 箇所だけを直すと、次のレビューで同じ観点の指摘が別の箇所から出る
3. 設計メモに反映し、手順 6 の自己レビューをやり直す
4. 報告は 1 回にまとめる。指摘ごとに `指摘 — 検討済み / 検討漏れ — 対応` を 1 行で書き、
   人間に聞くものは出力規約の質問の形で末尾に並べる。本文が手順 7 の再提示に当たる
   変わり方をしたら、同じ報告の中で承認を求める

「設計時点でどう考えていたか」と問われたら、検討記録の該当行を示す。行が無ければ検討漏れと
答え、同じ報告の中で上の 1 から進めた結論を示す。「どうしますか」だけを返さない。

## やらないこと

- 実装・ブランチ作成（`issue-implement` の領分）
- 人間の承認を得ていない起票
- 実装の細部（クラス名・関数名・画面文言）の作業アイテムへの記述
- 検証できない受け入れ基準の記述
- 根拠の無い「該当なし」、結論の無い観点を残したままの本文の提示
- 推奨の無い仕様の質問、委ねられた範囲の事項の質問
- 作業アイテムの状態の更新
- 確認していない影響・利用者像・画面名の記述
