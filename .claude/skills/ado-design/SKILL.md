# 設計 — アイデアを作業アイテムに落とす

人間の粗いアイデアを起点に、対話と調査を経て、実装に着手できる作業アイテムを作るまでの
手順。出力は実装工程（兄弟スキル `ado-implement`）の入力になる。あちらの手順 2 が
「受け入れ基準が空なら止まる」と定めている以上、ここで作る作業アイテムは受け入れ基準
まで埋まっていなければ意味がない。

## この段の入口

入口条件: **解決したいことはあるが、受け入れ基準の埋まった作業アイテムが無い**
（ループの定義は `../azure-devops/references/loop.md`）。条件が違う依頼は該当する段に渡す。

- 受け入れ基準の埋まった作業アイテムが既にあり、実装を求められている → `ado-implement`
- プルリクエストのレビュー → `ado-review`、レビュー指摘への対応 → `ado-fix`

起点はチャットの依頼でも、粗く起票済みの作業アイテムでもよい。作業アイテムが起点なら
`wit get` と `wit comments` で読んでから始める。

## 能力層

Azure DevOps の操作（`wit …` / `pr …` / `build …`）はすべて兄弟スキル `azure-devops` の
`scripts/ado.py` を通す。コマンドの一覧・セットアップ・フィールドの調べ方は
`../azure-devops/SKILL.md`。兄弟配置（同じ skills ディレクトリ直下）が前提。

## 出力規約

書き方は `../azure-devops/references/writing.md`。この手順固有の上限は次の 4 つ。

- 人間への質問はまとめて最大 5 件、1 件 1 行。小出しにせず 1 往復で潰す
- 方針の選択肢は最大 3 案。1 案 1 行の比較に収め、推奨に印をつける
- 設計判断として作業アイテムに書くのは最大 3 件。**覆すと手戻りになるものだけ**
- 受け入れ基準が 8 件を超えたら、基準を削るのではなく作業アイテムの分割を疑う

## 手順

### 1. 解決したいことを聞き取る

アイデアは「何を作るか」の形で来ることが多い。実装に落とす前に「何を解決するか」に
引き直す。作るものが同じでも、解決したいことが違えば受け入れ基準が変わる。

次の 3 つを依頼者との対話で確認する。

- **何を解決するか** — 今、誰が、何に困っているか。今はどう凌いでいるか
- **決まっていること** — 依頼者の中で確定していて、覆してはいけないこと
- **委ねられていること** — こちらの調査と提案で決めてよいこと

答えが本文から読み取れるなら聞かない。曖昧な点だけを質問にして、まとめて 1 往復で
確認する。解決したいことが確認できないまま先へ進まない。作り方の議論は解決したい
ことが定まってからで、逆順にすると選択肢の比較軸が作れない。

### 2. 既存を調べる

コードベースの読解を主にする。ネットワークが社内に閉じている場合、外部の検索や取得は
使えない。到達できない情報源を前提にした計画を立てない。

- 同じ課題を扱った作業アイテムが既に無いか `wit query` で探す（WIQL は
  `../azure-devops/references/recipes.md`）。重複や過去の見送りが見つかれば、それ自体が
  判断材料になる
- 実現方法の候補を、既存コードのどこに乗るかまで特定する。ファイルを開かずに挙げた
  候補は選択肢ではなく想像で、選ばれた後で覆る

### 3. 方針の選択肢を出し、人間が選ぶ

調査で得た選択肢を最大 3 案、1 案 1 行の「案 — 利点 / 欠点」で並べ、推奨に印をつける。
覆すと手戻りになる懸念があれば 1 件 1 行で添える。

**選ぶのは人間。ここで止まり、選択を待つ。** 実質 1 案しかないときは選択肢の形を
やめ、その方針と根拠を示して異議がないかだけ確認する。

方針と一緒に、クラス名・関数名・画面文言といった実装の細部を出さない。それは実装
工程の裁量で、ここで固定すると判断材料が実装案の中に埋もれる。

### 4. 作業アイテムの本文を書き、承認を得る

型ごとのフィールドは `wit describe-type` で確認する（`../azure-devops/SKILL.md` の
「最初にフィールドを調べる」）。書くのは次の 4 つ。

- **タイトル** — 解決することを書く。実現手段をタイトルにしない
- **説明** — 背景（なぜやるか）とスコープ外。手順 1 で確認した「解決したいこと」を
  ここに残す。実装する人が読むのは作業アイテムだけで、この対話は残らない
- **受け入れ基準** — 1 件 1 行、満たされたかを検証できる文で書く。
  `ado-implement` の手順 4 はこの 1 件ごとにテストを割り振る。「〜できること」で
  終わる曖昧な文は割り振れず、そこで実装が止まる
- **設計判断** — 手順 3 で人間が選んだ方針と、覆すと手戻りになる決定だけ。最大 3 件

1 つの作業アイテムは、独立してレビューできる 1 本のプルリクエストで完了する粒度に
する。超えるならフィーチャーを親にして子ストーリーに分割し、子の間に実装順の依存が
あれば親の説明に 1 行で書く。

起票の前に本文を依頼者に見せて承認を得る。`html` 型フィールドは起票後に読んで書き
戻す修正ができないため（`../azure-devops/SKILL.md`）、本文は起票前に固めるのが安い。
軽微な修正指示はそのまま反映して起票してよく、再提示は要らない。

### 5. 起票して報告する

```
wit create --type "User Story" --title "…" --description @body.md \
  --field-multiline Microsoft.VSTS.Common.AcceptanceCriteria=@criteria.md
wit create --type "User Story" --title "…" --parent <親id> …
```

分割した場合は親フィーチャーから先に作り、子は `--parent` でぶら下げる。起点が既存の
作業アイテムなら、そこに `wit comment` で起票した ID と URL を 1 行ずつ報告する。

`System.State` は触らない。いつ誰が状態を動かすかは組織の運用で決まっている。

## やらないこと

- 実装・ブランチ作成（`ado-implement` の領分）
- 人間の承認を得ていない起票
- 実装の細部（クラス名・関数名・画面文言）の作業アイテムへの記述
- 検証できない受け入れ基準の記述
- 作業アイテムの状態の更新
- 確認していない影響・利用者像・画面名の記述
