# 修正 — レビュー指摘に対応する

PR に付いた指摘を読み、同じブランチに修正を push し、対応内容を報告するまでの手順。
GitHub でも Azure DevOps でも同じ手順で動く。

## この工程の入口

入口条件: **未解決の指摘があり、依頼者が直す側** (ループの定義は中央リポジトリ
ai-workflows の `docs/loop.md`)。条件が違う依頼は該当する工程に渡す。

- レビューする側 → レビューの工程
- PR がまだ無い → 実装は `issue-implement`、設計は設計の工程

## 能力層

基盤ごとに違う操作は、この本文に「PR の指摘を読む」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

Git の操作 (checkout / diff / commit / push) は `git` CLI を使う。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 判断保留がある | 報告して、依頼者の回答を待つ | 報告に「決めてほしいこと」を書き、ワークフローの指示どおりに止まる |

PR の状態 (GitHub のラベル `ai:fix` / `ai:needs-human` など) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。

## 出力規約

`output-contract` スキルを前提とする。この工程固有の上限は次の 2 つ。

- 報告コメントは折りたたみの外を **合計 20 行以内**。読み手が見るのは「指摘が捌けたか」
  「まだ自分が決めることが残っているか」の 2 点だけ
- 何をどう直したかは差分にある。文章で言い換えない

## 手順

### 1. 対象を特定する

「PR を読む」でソースブランチとターゲットブランチを控え、ソースブランチを最新にして
checkout する。

```
git fetch origin
git checkout <ソース> && git pull
```

### 2. 指摘と人間のコメントを読む

「PR の指摘を読む」で、トップレベルと差分の行の両方のコメントを読む。人間の判断が
行コメントや解決済みのスレッドに残っていることがある。

規約も読む。

- リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
  従う
- コードコメントや docs を触るときは `artifact-writing` スキルに従う
- コミットメッセージは `git-conventions` スキルに従う。指摘対応であることは type にしない。
  直した内容で type を決める

### 3. 差分を把握する

```
git diff origin/<ターゲット>...origin/<ソース>
```

何が変更済みかを知らずに指摘だけ読むと、既に直っているものを直す。

### 4. 指摘を分類する

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| 対応する | 妥当な指摘 | 直す |
| 対応しない | 人間が「対応不要」「仕様どおり」と明示している | 触らない |
| 判断保留 | 仕様の判断が要り、正解が一意に決まらない | 直さず、決めてほしいこととして出す |

**人間のコメントが常に最優先。** レビューの指摘と人間のコメントが食い違ったら人間に従う。

迷ったら「判断保留」に倒す。独断で埋めた仕様は差分の中に紛れ、次のレビューでも仕様の誤りと
しては現れない。

### 5. 指摘ごとに検証を割り振り、落ちるテストを書く

「対応する」に分類した指摘 1 件ごとに、次の 4 つのどれかを割り振る。この割り振りがそのまま
手順 9 の報告の表の検証欄になる。全件に割り振りが付くまで手順 6 に進まない。

- **新規テスト** — 誤動作の指摘。その誤動作で落ちるテストを 1 本書き、実行して落ちることを
  確認する。落ちない、または「まだ直していないから」以外の理由 (import エラー、設定の不備)
  で落ちるテストは、その指摘を検証していない
- **既存テスト** — その誤動作を検証するテストが既にある。テスト名を控える
- **検証不要** — 誤動作ではない指摘 (書式・命名・重複など)。直す前に落ちるテストが書けない
  ものに限る。分類名ではなく指摘の中身で決める。条件を挙げて誤りを述べている指摘は、分類が
  「重複」でも誤動作
- **基盤なし** — リポジトリにテストの実行コマンドが無い (CI 設定・パッケージのスクリプト
  定義・テストランナーの設定のいずれにも無い)。基盤の新設はしない

判定はリポジトリ単位。対象のファイルに既存のテストが無いことは「基盤なし」の理由に
ならない。テストファイルを新しく作るのは基盤の新設ではない。足すのは誤動作を再現する
1 本にとどめ、周辺の未テスト箇所には広げない。

**テストを書くのは直す前のここ。** 直した後に書いたテストは修正後の実装をなぞるだけで、
誤動作を再現しない。落ちることを確認していないテストは、通っても何も保証しない。

### 6. 優先度の高いものから直す

P0 → P1 → P2 の順に着手する。途中で打ち切られても P0 が片付いている状態にするため、順序を
崩さない。優先度が付いていない指摘は、壊れる度合いで自分で順序を付けてから着手する。

指摘に修正案があれば、推奨として示された案を第一候補にする。代案を採る場合、どれも採らない
場合は、その理由を報告に 1 行書く。

指摘と無関係な改善はしない。気づいた点は報告の末尾に 1 行で残す。

### 7. テストを通す

手順 5 のテストと既存のテストを実行して通す。テストを通すためにテスト自体を書き換えない。
実装を直せないなら「判断保留」に回す。

### 8. 同じブランチに push する

変更したファイルを名指しして `git add` し、コミットして push する。

```
git push origin HEAD
```

新しいブランチを作らない。force push しない。ターゲットブランチへ直接 push しない。

### 9. 報告する

「PR にコメントする」で次の形の報告を残す。

```
| 指摘 | 対応 | 検証 |
|---|---|---|
| src/a.ts:42 の 0 除算 | 修正 | tests/a.test.ts の rejects-zero-divisor |
| 命名の統一 | 見送り — 人間が「対応不要」と判断済み | 検証不要 |

**決めてほしいこと**
1. 〜を A / B どちらにするか (A: …、B: …)
```

- 表は 1 指摘 1 行。対応欄は「修正」か「見送り — 理由 1 句」だけ。直し方は書かない
- 検証欄には手順 5 の割り振りを書く。新規テスト・既存テストはテスト名まで、残りは
  「検証不要」「基盤なし」の 1 語。**空欄にしない。**「修正」の行の検証欄が埋まらないなら、
  報告を書かずに手順 5 に戻る
- 「決めてほしいこと」は判断保留があるときだけ。1 件 1 行で選択肢と帰結を並べ、推奨は
  付けない。決めるのは人間
- スレッドを解決済みにしない。指摘が解消したかを判断するのは指摘した側

判断保留が 1 件でもあるなら、報告したところで止める。回答を待たずに次へ進まない。

## やらないこと

- 指摘と無関係な変更・リファクタリング・新機能の追加
- 新しいブランチの作成、force push、ターゲットブランチへの push
- PR の承認 (approve・投票)・マージ (完了)・破棄
- レビュースレッドの解決済み化 (指摘が解消したかを判断するのは指摘した側)
- 人間が「対応不要」と判断した指摘への対応
- テストを通すためのテスト自体の書き換え
- 修正した後に書いたテストを「検証」として報告すること
- 検証欄を空けたままの報告
