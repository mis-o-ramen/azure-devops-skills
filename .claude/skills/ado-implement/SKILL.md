# 実装 — 作業アイテムを実装する

作業アイテムを読み、実装し、プルリクエストを作るまでの手順。

## この段の入口

入口条件: **受け入れ基準の埋まった作業アイテムがあり、プルリクエストが無い**
（ループの定義は `../azure-devops/references/loop.md`）。条件が違う依頼は該当する段に渡す。

- 作業アイテムが無い、または受け入れ基準を書き起こすところから → `ado-design`
- プルリクエストのレビュー → `ado-review`、レビュー指摘への対応 → `ado-fix`

依頼の中の数字だけのファイル名（`2251.md` など）や裸の数字は作業アイテム ID である
ことがある。`wit get` で引き当ててから始める。

## 能力層

Azure DevOps の操作（`wit …` / `pr …` / `build …`）はすべて兄弟スキル `azure-devops` の
`scripts/ado.py` を通す。コマンドの一覧・セットアップ・フィールドの調べ方は
`../azure-devops/SKILL.md`。兄弟配置（同じ skills ディレクトリ直下）が前提。
Git 操作（clone / diff / branch / commit / push）は `git` CLI を使う。ブランチ名と
コミットメッセージの規約は `../azure-devops/references/git.md`。

## 出力規約

書き方は `../azure-devops/references/writing.md`。この手順固有の上限は次の 3 つ。

- 説明の**見出し**はリポジトリの PR テンプレートに合わせる。足さない・改名しない
  （`.azuredevops/pull_request_template.md` / `.github/pull_request_template.md`）。
  ここで定めるのは各欄の件数と行数だけ
- プルリクエストの説明は合計 25 行以内。実装量が多くても説明は増やさない
- 変更ファイルを列挙しない。プルリクエストの画面が既に表示している

## 手順

### 1. 満たすべき条件を読む

```
wit get <id> --relations
wit comments <id>
```

受け入れ基準のフィールドは型ごとに違う。参照名を推測せず `wit describe-type` で確認する
（`../azure-devops/SKILL.md` の「最初にフィールドを調べる」）。ユーザーストーリーなら
`Microsoft.VSTS.Common.AcceptanceCriteria`、バグなら `Microsoft.VSTS.TCM.ReproSteps` に
条件が入っていることが多い。

`relations` に親（フィーチャーなど）があれば辿って読む。作業アイテム 1 件には「何を」しか
書かれておらず、「なぜ」は親にある。コメントも読む。フィールドの本文より新しい決定が
ディスカッションに残っていることがある。

### 2. 条件が足りなければ止まる

受け入れ基準が空、または実装が一意に決まらないなら、推測で実装しない。不足している条件を
1 件 1 行で挙げて `wit comment` で投げ、そこで止める。

独断で埋めた仕様は差分の中に紛れる。レビューはコードの誤りは見つけるが、書かれなかった仕様の
誤りは見つけない。

### 3. ブランチを切る

命名は `../azure-devops/references/git.md`。ターゲットブランチの最新から切り、
作業アイテム 1 件に 1 ブランチにする。

### 4. 全基準に検証を割り振り、落ちるテストを書く

受け入れ基準 1 件ごとに、次の 4 つのどれかを割り振る。この対応がそのまま手順 8 の
「受け入れ基準と検証」の表の行になる。全基準に割り振りが付くまで手順 5 に進まない。
「手間がかかる」は割り振れない理由にならない。

- **既存テスト** — 基準を検証するテストが既にある。テスト名を控える
- **新規テスト** — 基準が満たされていないことで落ちるテストを書き、実行して落ちることを
  確認する。落ちない、または「未実装だから」以外の理由（import エラー、設定の不備）で
  落ちるテストは、その基準を検証していない
- **プレースホルダ** — 実装前には落ちるテストが書けない基準（実装後に生まれる関数や
  エンドポイントを呼ぶものなど）。テストランナーの skip 指定で骨組みだけ置き、手順 6 で
  実装済みのテストに置き換える
- **自動テスト不能** — 次の 3 つのどれかに当たる基準だけ。skip 指定のテストを、該当する
  1 語と根拠を理由に付けて残す
  - `手動のみ` — 目視や操作でしか確認できない。手順 8 の手動確認手順に転記する
  - `対象外` — テスト基盤がその層を実行できない（UI 描画など）
  - `外部依存` — テスト環境に無い依存を 1 つ名指しする

テストの実行コマンドが無いリポジトリ（CI 設定・パッケージのスクリプト定義・テストランナー
の設定のいずれにも無い）では、この手順を飛ばして全基準を手動確認に割り振り、テスト基盤が
無いことを「受け入れ基準と検証」の表に書く。基盤の新設はしない。

既存のテストは書き換えず、追加で書く。

### 5. 最小の変更を実装する

リポジトリに `CLAUDE.md` などの規約があれば読んで従う。

受け入れ基準を満たす最小の変更にとどめる。スコープ外の改善は入れず、気づいた点は手順 9 の
作業アイテムのコメントに回す。説明にテンプレートに無いセクションを作らない。

コミットする成果物（コード・コメント・docs）は現在形で書く。「以前は」「〜に変更した」と
いった経緯を成果物に残さない。経緯はプルリクエストの説明に置く。

### 6. テストを通し、プレースホルダを回収する

4 で書いたテストと既存のテストを実行して通す。テストを通すためにテスト自体を書き換えない。
期待値が誤っていたと分かったときだけ直し、その旨を説明の自律判断した箇所に書く。実装を
直せないなら止まり、`wit comment` で投げる。

4 でプレースホルダにした基準は、ここで実装済みのテストに置き換える。期待値は実装の出力を
写さず、受け入れ基準の文言から書く。skip のまま残してよいのは自動テスト不能の 3 語の理由が
付いたものだけで、「実装前に書けなかった」はここでは理由にならない。

### 7. コミットして push する

```
git add <変更したファイル>
git commit -m "…"
git push -u origin HEAD
```

コミットメッセージの書式は `../azure-devops/references/git.md`。push するのは手順 3 で
切ったブランチだけで、ターゲットブランチへは直接 push しない。

push 済みのコミットは書き換えない。まとめ直すなら push の前に済ませる。

### 8. 承認を得てプルリクエストを作る

プルリクエストの作成はレビュアーへの通知を伴い、エージェントからは取り消せない。
作成の前に、次の 2 つを順に通す。

- **完了の確認** — 手順 4 の割り振りが全基準に付き、手順 6 のテストが通っている。
  欠けたまま作らない。進められない理由があるなら、プルリクエストを作らずに
  `wit comment` で報告して止まる
- **本文の承認** — タイトル・説明・ソース / ターゲットブランチを依頼者に提示し、
  承認を得る。`pr create` は既定でドラフトを作るので、`--publish` を付けるのは
  承認を得たときだけ。承認を得られない非対話の実行では既定のまま（ドラフト）作り、
  公開の判断を人間に残す

```
pr create --repo <repo> --source <type>/wi-<id>-<slug> --target <ターゲット> \
  --title "…" --description @body.md --work-item <id> --publish
```

`--work-item` で作業アイテムに紐づける。紐づいていればレビュー側が `pr workitems` で受け入れ
基準を読める。省くとレビューは差分しか見られない。

説明の見出しはリポジトリの PR テンプレートに従い、そこに無いセクションを作らない。
テンプレートが無ければ次の 5 つを使う。HTML コメント（`<!-- -->`）は記入後に消す。

- **変更概要** — 何を、どう解決したか。**3 行以内**。下のレビュ要点を読むための前置きで
  あって、差分の言い換えではない
- **レビュ要点** — 次の 2 つだけを入れる小見出しで、それ自体に本文を書かない
  - **自律判断した箇所** — 作業アイテムに指示が無く、自分の判断で決めた点。最大 3 件、
    1 件 1 行、確信が低いものから順に。無ければ「該当なし」と書く
  - **未検証の受け入れ基準** — 下の表で「未検証」とした基準の再掲と、skip の理由
    （手動のみ / 対象外 / 外部依存）1 行。無ければ「該当なし」と書く
- **受け入れ基準と検証** — 1 基準 1 行の表（基準 / 検証方法 / 結果）。検証方法は差分内の
  テストのパス（テスト名まで）か手動確認の内容。結果は OK / NG / 未検証 のいずれかで、
  OK と書けるのはそのテストを実行して通ったものだけ。未検証の行は消さず、検証方法に
  skip したテスト名と理由を書く
- **設計判断** — 実装から読み取れないものだけ、最大 3 件、1 件 1 行。「なぜ他の案を採らな
  かったか」が 1 行で書けるものに限る。自明な実装に判断はない。無ければ見出しごと削除する
- **手動確認手順** — CI が見ない範囲を人が再現する手順。不要なら「不要」と書く

変更概要のすぐ下に自律判断と未検証を置くのは、**レビュアーが差分を読んでも分からないのが
そこだけ**だから。指示が無かった箇所は差分の上では指示どおりの実装と見分けが付かず、
未検証が妥当かは skip の理由を差分と突き合わせないと判断できない。人間の注意力は下へ行くほど
落ちるので、人間にしか決められないものをできるだけ上に置く。

**変更概要が 3 行なのはそのため。** 何の変更か分からなければ下の判断材料が何についての
判断か決まらないので前置きは要るが、3 行を超えた分はそのまま判断材料を下へ押し下げる。

**「該当なし」と書かせるのは自律判断と未検証の 2 つだけ。** 空欄だと、判断が無かったのか
書き忘れたのかを読み手が区別できない。設計判断は逆に、無ければ見出しごと削除する。
残すと埋めたくなり、埋めるために生成された設計判断は本物を薄める。

### 9. 作業アイテムに報告する

```
wit comment <id> --text "…"
```

プルリクエストの URL と 1 行のサマリだけ。説明の内容を作業アイテム側に繰り返さない。両方に
書けばどちらかが必ず古くなる。手順 5 でスコープ外に気づいた点があれば、最大 3 件、
1 件 1 行で添える。説明には入れない。

`System.State` は触らない。いつ誰が状態を動かすかは組織の運用で決まっている。

## やらないこと

- 人間の承認を得ていないプルリクエストの作成（非対話の実行ではドラフトに倒す）
- 受け入れ基準の検証が終わっていない状態でのプルリクエストの作成
- force push、ターゲットブランチへの直接 push
- 作業アイテムに書かれていない機能の追加
- 依存パッケージの大規模な追加・更新（必要なら作業アイテムのコメントで提案に留める）
- テスト基盤・テストフレームワークの新設
- テストを通すためのテスト自体の書き換え
- プルリクエストの完了・破棄・投票
- 成果物への経緯の記述
