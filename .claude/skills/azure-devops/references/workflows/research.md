# 調査して報告する

コードを変更せずに調べ、作業アイテムのコメントで報告するまでの手順。

## 出力規約

書き方は `../writing.md`。この手順固有の上限は次の 2 つ。

- 本文は合計 30 行以内。調べた量ではなく、決めるために必要な量を書く
- 作業アイテムのコメントに折りたたみは使えない。畳めない以上、根拠は省くしかない。長い根拠が
  要るならファイルに書いて、その場所を 1 行で示す

## 手順

### 1. 何を決めるための調査かを特定する

```
wit get <id>
wit comments <id>
```

決めたいことが分からないまま調べると、読み手が使えない報告になる。依頼が曖昧なら、調べる前に
「何を決めたいか」を `wit comment` で確認する。

### 2. 調べる

コードベースの読解を主にする。ネットワークが社内に閉じている場合、外部の検索や取得は使えない。
到達できない情報源を前提にした計画を立てない。

同じ調査が既に作業アイテムに残っていることがある。`wit query` で先に探す（WIQL は
`../recipes.md`）。

### 3. 断定できることと、できないことを分ける

確認した範囲でしか断定しない。「たぶん」で書いた結論は、そのまま意思決定に使われる。

断定できないなら、断定できないことと「何が分かれば決まるか」を書く。それ自体が次の行動になる。

### 4. 報告する

```
wit comment <id> --text @report.md
```

- **結論** — 3 行以内。断定できないなら、その旨と何が足りないかを書く
- **判断材料** — 選択肢があるときだけ。1 案 1 行で「案 — 利点 / 欠点」。最大 4 案
- **推奨アクション** — 最大 3 件、1 件 1 行。人間が次に取る行動として書く

表は作業アイテムのコメントでは崩れる。記号で区切って 1 行にまとめる。

作業アイテムを新規に起票しない。実装タスクに落とせそうなら、タイトルと受け入れ基準の案を
推奨アクションに 1 行で示すに留める。起票するかどうかは人間が決める。

## やらないこと

- ファイルの作成・編集
- 作業アイテムの新規作成、状態の更新
- 確認していない影響・利用者像・画面名の記述
