# 報告の書き方

どの手順でも、書いたものを読むのは人間で、その時間がボトルネックになる。結論や指摘そのものを
薄くしないまま、読む量を抑える。各手順のファイルは、これに加えて固有の上限を定める。

## 原則

- **結論を先頭に置く。** 読み手が最初の 3 行で次の行動を決められること
- **確証のないことを書かない。** 機能名・利用者像・影響は、差分・コード・作業アイテムから
  確認できたものだけを書く。断定できないときは条件付きにするか、その欄ごと省く。埋まって
  いない欄より、埋まっている誤りのほうが高くつく
- **本文にコードを引用しない。** 箇所は `path:line` で示せば読み手は開ける
- **該当のないセクションは見出しごと省く。** 「特になし」も 1 行のコスト。例外は
  テンプレートが「該当なし」と書くよう求めている欄だけ。そこを省くと、該当が無かったのか
  書き忘れたのかを読み手が区別できない
- **上限は水増しの許可ではない。** 埋めるために内容を薄めない。厚く書きたいときは件数の
  上限を下げて総量を保つ
- **同じ内容を二箇所に書かない。** 作業アイテムとプルリクエストの両方に書くと、どちらかが
  必ず古くなる
- **「まとめ」「所感」「良い点」を書かない。** 判断に寄与しない

## 投稿先ごとの制約

| 投稿先 | コマンド | 書式 |
| --- | --- | --- |
| プルリクエストのコメント | `pr comment` | Markdown が効く。表・箇条書き・コードブロックを使える |
| 作業アイテムのコメント | `wit comment` | プレーンテキストとして入る。記号はエスケープされ、表は崩れ、折りたたみは使えない |

作業アイテム側に長文を置かない。詳細はプルリクエストに置き、作業アイテムにはリンクと結論だけ
書く。畳めない以上、根拠は省くしかない。
