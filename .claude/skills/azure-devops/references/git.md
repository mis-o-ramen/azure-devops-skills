# ブランチ名とコミットメッセージ

作業対象のリポジトリで実装・修正するときの、ブランチ名とコミットメッセージの規約。
工程スキル（`issue-implement` / `pr-fix`）は同じ内容の `git-conventions` スキルを読む。ここは工程スキルを通さずにコミットするときの規約。差分の取得手順はここに置かない。

## リポジトリの既存規約が優先

上から順に見て、最初に決まったものに従う。全部外れたときだけこの文書が効く。

1. `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` の明文の規約
2. `CONTRIBUTING.md`、またはそこから参照される規約
3. commitlint / commitizen / husky などの設定。機械検査が既に規約になっている
4. `git log --oneline -30` と `git branch -r --sort=-committerdate` の実態。直近 30 件の
   過半数が同じ書式なら、それが規約

書式を上書きすると履歴が 2 つの書式に割れ、種類での絞り込みがどちらの書式でも漏れる。
機械検査に反する書式は push か CI で落ちる。

## type

ブランチ名とコミットメッセージで同じ語を使う。次の 7 語だけを使い、増やさない。

| type | 使う場面 |
| --- | --- |
| `feat` | 利用者に見える機能の追加・変更 |
| `fix` | 誤動作の修正 |
| `refactor` | 外から見た振る舞いを変えない内部の変更 |
| `test` | テストだけの追加・修正 |
| `docs` | ドキュメント・コメントだけの変更 |
| `build` | 依存・ビルド設定・CI の変更 |
| `chore` | 上のどれでもない雑務 |

語を増やさないのは、同じ変更に複数の名前が付くと type で絞り込めなくなるため。`perf` は
`feat` か `refactor`、`style` は formatter の領分で人が打つコミットにならない、`ci` は
`build` に含める。

迷ったときの寄せ方。

- 利用者の目に見える変化があるなら `feat`、無いなら `refactor`
- 誤動作を直したなら `fix`。誤動作でない改善は `fix` にしない
- テストと実装が同じコミットに入るなら実装側の type を採る。`test` はテストだけのとき
- レビュー指摘への対応でも、直した内容で type を決める。指摘対応であることは type ではない
- 2 つの type にまたがるなら、コミットを分ける機会。分けられないなら主たるほうを採る

## ブランチ名

`<type>/wi-<id>-<slug>`。例 `feat/wi-2251-csv-export`。

| 要素 | 規則 |
| --- | --- |
| `<type>` | 上の表の語。その作業**全体**の主たる変更に合わせる |
| `wi-<id>` | 作業アイテムの ID。`wi-` は固定 |
| `<slug>` | 英小文字・数字・ハイフンだけ。2〜4 語、24 文字以内 |

- 作業アイテム 1 件に 1 ブランチ。混ぜると、プルリクエストを受け入れ基準と 1 対 1 で
  突き合わせられなくなる
- 作業アイテムのタイトルが日本語なら、内容を表す英語 2〜4 語を選ぶ。ローマ字に転写しない。
  非 ASCII のブランチ名は環境によって扱いが割れる
- 迷ったら短くする。ブランチ名は識別のためにあり、説明は作業アイテムにある
- **修正の段はブランチを切らない。** `sourceRefName` に checkout する。既存ブランチ名が
  この形式でなくても改名しない。改名はプルリクエストを壊す

## コミットメッセージ

### 要約行

`<type>(<scope>): <日本語の要約>`

- 50 文字以内。超えるならコミットが大きい
- 常体の現在形。動詞で終わるか体言止めにする。「〜しました」「〜した」にしない
- 末尾に句点を付けない
- `<scope>` は任意。付けるなら 1 語で、対象リポジトリで既に使われている語だけ。無理に
  付けない

### 本文

要約行の次に空行を 1 つ置き、72 文字前後で折る。合計 10 行以内。

書くのは、要約行から読めない「なぜその変え方にしたか」だけ。何を変えたかは書かない。
差分にある。変更全体の経緯・自律判断・受け入れ基準との突き合わせはプルリクエストの説明に
置く（`writing.md`「同じ内容を二箇所に書かない」）。

### 粒度

- 1 コミット 1 目的。テストが通っている必要があるのはブランチの先頭だけで、落ちるテスト
  だけのコミットが途中にあるのは構わない
- push 前に限り、途中のコミットはまとめてよい。push 済みのコミットは書き換えない。
  書き換えは force push になり、取得済みの履歴を壊す
- `git add` は変更したファイルを名指しする。`-A` は生成物やローカル設定を巻き込む

### 書かないもの

- **作業アイテムの ID** — ブランチ名が持ち、プルリクエストは `--work-item` で紐づいている。
  同じ ID を 3 箇所に書いても、増えるのは書き間違いの機会だけ
- **生成ツール名・エージェント名・セッション URL・署名行** — 手順は道具非依存で、署名を
  入れると実行した道具ごとに履歴の書式が割れる。誰が push したかはサーバに残る
- `wip` / `fixup` / `修正` / `update` のような、何になるか読めない要約行

## 経緯をどこに置くか

| 置き場 | 書くもの | 書かないもの |
| --- | --- | --- |
| 成果物（コード・コメント・docs） | 今どうなっているか | 経緯、以前の状態 |
| コミットメッセージ | そのコミットで何になるか。なぜその変え方か | 差分の言い換え、作業の途中経過 |
| プルリクエストの説明 | 変更全体の経緯、自律判断、受け入れ基準との突き合わせ | コミット単位の詳細 |

成果物は現状を知るために読まれ、履歴は遡るために読まれる。経緯を成果物に置くと現状を読む
邪魔になるが、履歴に置けば遡る人だけが読む。

## 例

```
feat/wi-2251-csv-export
feat(export): 集計結果を CSV で書き出せるようにする
```

| 悪い例 | 何が悪いか |
| --- | --- |
| `ai/wi-2251` | type が無く、どの種類の作業か履歴から分からない |
| `feature/2251_CSV出力` | 表にない接頭辞。`wi-` が無い。slug が日本語 |
| `fix: 修正` | 何が直るのか読めない |
| `feat: CSV出力を追加しました。` | 敬体と句点 |
| `fix: バグを修正 #2251（generated by …）` | ID の重複と署名 |
