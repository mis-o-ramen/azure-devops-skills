# 成果物の記述規約

コード・ドキュメントなど、**後から他人（未来の自分を含む）が読む成果物**に何を書き、何を書かないかを定める。

原則は1つ。**成果物は現在形で書く。**
規範と、その規範が今も成り立つ理由だけを置き、そこに至った経緯は置かない。

## 3層に分ける

| 層 | 内容 | 成果物 | 行き先 |
|---|---|---|---|
| **規範** | 何をするか / してはいけないか | 書く | — |
| **根拠** | なぜその規範が成り立つか | 書く（現在形・一般化） | — |
| **顛末** | どうやってその規範に至ったか | **書かない** | issue / PR本文 |

### 根拠は削らない

「なぜ」を消すと、次に読んだ人が善意で規範を「直して」しまう。
根拠は規範の一部であり、削減の対象ではない。削るのは顛末だけ。

### 顛末の見分け方（時制で判定する）

以下が出たら顛末。機械的に検出できる。

- 過去形: 「〜だった」「〜していた」「〜になっていた」「〜と言っていた」
- 時間の副詞: 「かつて」「以前は」「元々」「最初は」「一度」「最後に」
- 固有の事件への参照: `PR #47`、`issue #53`、「検出器の◯◯を踏んでいる」、「実際 `#a97b22` は」
- 過去の悪い実例の引用（直った文言・値・コードの現物）

上のリスト内の番号・色値・クラス名は検出パターンの例示であり、成果物の本文に実値で書いてよいという意味ではない。

## 顛末を根拠へ翻訳する

顛末は捨てるのではなく、**現在形の一般則に書き換えて**残す。事実は保存され、事件だけが消える。

| 成果物 | 顛末（書かない） | 根拠（書く） |
|---|---|---|
| 設計ドキュメント | 白地基準で決めた値が、淡地で AA を割っていた | 意味色のコントラストは、その色が実際に載る地の上で測る |
| コードコメント | タイムアウト3秒で本番が落ちたので10秒にした | 外部APIの p99 が8秒前後なので10秒 |
| README | v2で設定形式を変えたので旧形式のままだと動かない | （現行の形式だけを書く。旧形式には触れない） |
| 型定義 | 互換のために残したフィールド。#123 で削除を見送った | `deprecated` の一語と、削除予定のバージョン |
| 規範ドキュメント | 文章の層だけが規範を持たずドリフトしていた | （規範の無い層はドリフトする — 自明なので**書かない**） |

最後の行が示すとおり、翻訳した結果が**自明な一般論にしかならないなら、それは根拠ではなく動機**。丸ごと落とす。

例は自分のリポジトリの実例に差し替えてよい。ただし差し替えるときは、**その1件を知らない読者にも一般則が読み取れる形**にする。特定の色値・クラス名・PR番号がそのまま残っていたら、例ではなく顛末が紛れ込んでいる。

## 例外: 再発防止のために顛末が要るとき

規範だけでは同じ誤りが繰り返されると判断できる場合に限り、**禁止形の1行**として書く。物語にはしない。

- ✅ 「`h1` を `text-lg` に落とさない」
- ❌ 「一度 `text-lg` に揃えて検出器を踏んでいるので、`h1` は `text-lg` にしない」

## 成果物ごとの適用

- **規範ドキュメント（DESIGN.md 等）**: 各ルールは「規範 → 根拠」の2文まで。移行の経緯・旧値・旧文言を載せない
- **README**: 現在の使い方のみ。過去のAPI、廃止した手順、移行の理由を書かない（それはCHANGELOG）
- **コードコメント**: そのコードが**今なぜそうなっているか**のみ。「以前は〜だったが」「〜のバグを踏んだので」は書かない。修正の経緯は `git blame` から辿れる
- **型定義・スキーマ**: 制約と単位のみ。互換性のために残したフィールドは「deprecated」の一語で足りる
- **ADR**: 唯一、決定の時点を記録してよい成果物。ただし記録するのは**決定と選ばなかった選択肢**であって、議論の推移ではない

## 顛末の正しい行き先

顛末は価値がある情報なので、消すのではなく移す。

- **PR本文**: 何が壊れていたか、どう気づいたか、何を直したか
- **issue**: 発見の経緯、再現手順、検討の推移
- **ADR**: 方針を転換した場合の、決定とその時点の前提

成果物から顛末を落とすとき、**行き先を確保してから落とす**。移し先が無いなら、PR本文に書いてから成果物を書く。

### 逆流させない

行き先へ移した文を、成果物へ書き戻さない。**PR本文に書いた経緯の説明文を、コードコメントに再掲しない。**
実装と PR本文を続けて書くときに起きる。PR本文で正しい文が、同じ文のまま成果物では違反になる。

同じ事実を両方に置いてよいのは、**成果物側が現在形の根拠としてそれを要する**とき（単位・境界値・外部仕様の制約）だけ。
判断の経緯・調査の出どころ・直前の状態は、片方にしか置かない。

## セルフチェック

**コミットする前に、diff の追加行を点検する。** 文書を1本書き上げたときだけでなく、
コードの diff にコメントが1行混ざっただけのときも同じ点検を通す。点検の単位は文書ではなく diff。

まず機械で拾う。

```bash
git diff HEAD | grep '^+' | grep -E 'だった|していた|なっていた|かつて|以前は|元々|最初は|一度|引き続き|PR #|#[0-9]+ で'
```

`git diff HEAD` にするのは、staged と unstaged の両方を一度に見るため。

ヒットは顛末の候補であって確定ではない。**ヒットした行は、現在形へ翻訳してから通す**。
拾えるのは日本語の時制だけなので、grep が空でも下の目視は省かない。

- [ ] 過去形・時間の副詞が残っていないか
- [ ] PR番号・issue番号・過去の値・過去の文言が本文に混ざっていないか
- [ ] PR本文に書いた経緯の説明文を、コードコメントへ再掲していないか
- [ ] 各規範に、それが今も成り立つ根拠が付いているか（根拠を削りすぎていないか）
- [ ] 落とした顛末の行き先（PR本文 / issue）を確保したか
- [ ] その文書自身が定めているルールに、その文書が違反していない
