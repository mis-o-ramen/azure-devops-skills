# コーディング規約を整備する

規約は読ませるために書くのではなく、**判断がぶれる場面で同じ答えを出させるために**書く。その用を
果たさない行は、毎回読まれるコストだけを足す。

対象プロジェクトのコードが読める状態で実行する。読めないなら抽出ができず、この手順は成立しない。

## 書かないものを先に決める

書く候補より落とす候補のほうが多い。次に当てはまる行は入れない。

| 落とすもの | 例 | 理由 |
| --- | --- | --- |
| エージェントが既定で行うこと | 「DI を使う」「サーバ側でも入力を検証する」「層を分ける」 | 書いても書かなくても結果が変わらない |
| コードから読み取れること | 使用フレームワーク、UI ライブラリ、バージョン | 依存定義ファイルにある。二重管理になり、片方が古くなる |
| 一般論 | 「命名は分かりやすく」「責務を適切に分ける」 | 判断が分かれる場面で何も決めていない |
| 機械検査できること | インデント、`import` の順序、ファイル名の形式 | 設定ファイルに入れる。文章は破られても気づかないが、CI は気づく |
| 現に守られていないこと | 決めたが実装が従っていない規則 | エージェントはコードの実態に合わせる。食い違いはレビューの誤検知になる |

残るのは「機械検査できず、コードを見ても一意に決まらず、実際に判断がぶれるもの」だけ。だいたい
20〜40 項目に収まる。

## 埋める欄

**書けない欄は見出しごと省く。** 空欄を残すと、決まっていないのか無いのかが読み取れない。

| 欄 | 決めること |
| --- | --- |
| 層と依存の向き | どのディレクトリが何を持つか。**禁止する依存を名指しする**（「A は B を参照しない」） |
| 境界で渡すもの | 層やプロセスの境界で渡す型と、変換する場所 |
| エラーの扱い | 送出する場所、捕まえる場所、外に出る形。実装の実例を指す |
| 入力の検証 | どの入力を信頼しないか、どこで検証するか、失敗時に何を返すか |
| 画面の構成単位 | コンポーネントの粒度、状態を置く場所、データ取得を行う場所 |
| 見た目の指定 | スタイルの書き方を 1 つに決める。テーマの値を使う範囲と、直接指定してよい範囲 |
| 命名 | 機械検査に落とせない部分だけ。用語の統一、単数と複数、日本語と英語の使い分け |
| テスト | 必ず書く対象、書かない対象、モックしない対象、テストの境界 |
| 触らないもの | 生成物、移行済みの旧実装、外部仕様に固定された箇所 |
| 未確定 | 判断が付いていない論点。ここに書かれた論点だけが、エージェントに確認させられる |

バックエンドとフロントエンドで分けない。分けると層の境界・エラー・テストを 2 回書くことになる。
片方にしか存在しない欄は、その欄だけ対象を明記する。

## 手順

### 1. 実装から抽出する

各欄について、**同じやり方が 2 箇所以上ある**ものだけを候補にする。1 箇所しかないものは規約では
なく、その 1 箇所の事情。

新規プロジェクトで抽出元が無いなら、欄を空のまま置かない。最初の実装が入ってから戻る。

### 2. 意図か偶然かを確認する

抽出した候補を 1 項目 1 行で人間に見せ、意図してそうしているかを確認する。

| 回答 | 扱い |
| --- | --- |
| 意図 | 規約にする |
| 偶然 | 落とす |
| そうしたいが実装が従っていない | 規約に入れず、「未確定」に置くか、直す作業アイテムにする |

移行途中の規則を規約として書くと、既存コードのほとんどが違反になり、レビューが機能しなくなる。

### 3. 文章ではなく実例を指す

正しい実装が 1 箇所あるなら、手順を説明せず `path:line` を指す。文章は実装が変わっても追随
しないが、参照先はレビューと CI が守る。

### 4. 機械検査へ移す

linter / formatter / 型定義 / スキーマで検査できる項目は設定に移し、文章から消す。消し忘れると
同じ規則が 2 箇所にあり、片方だけが更新される。

### 5. 置き場所に書く

| 読み手 | ファイル |
| --- | --- |
| Claude | `CLAUDE.md` |
| GitHub Copilot | `AGENTS.md`、または `.github/copilot-instructions.md` |

両方で効かせるなら、実体を片方に置き、もう片方はそれを読ませる 1 行にする。同じ内容を 2 ファイル
に置くと、必ず片方が古くなる。

### 6. 上限を守る

本文は 150 行以内、1 項目 1〜2 行。毎回コンテキストに載るため、長さがそのままこのプロジェクトの
全作業のコストになる。超えたら項目を削るか、詳細を別ファイルに出して「該当する作業のときだけ
読む」形にする。

## 維持する

- レビューで同じ指摘が 3 回出たら規約に足す。3 回出る指摘は規約の欠落
- 規約と実装が食い違ったら、どちらを直すか決めてから進む。放置された食い違いは、以降すべての
  指摘の信頼度を下げる
- 足したときは、同じ回で何を落とせるかを見る。足すだけなら必ず肥大化する
