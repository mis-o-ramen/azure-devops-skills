# 開発ループ

ワークフローとスキルが仕えるループの定義。エージェントは段の中を自律で進み、
人間は段の境界にある承認点でループを制御する。

この定義は実行基盤に依存しない。GitHub ではラベルが段を起動し (HOTL)、
Azure DevOps ではチャットの依頼が段を起動する (HITL に近い)。段・入口条件・成果物・
人間が握る制御点は両方で同じで、違うのは「段を誰がどう起動するか」と
「承認をどう表すか」だけ。

## 全体像

```
アイデア ─[設計]→ チケット ─[実装]→ プルリクエスト ─(人間がマージ)→ 完了
                                        │      ▲
                                    [レビュー]  [修正]
                                        │      │
                                        └─ 指摘 ┘
```

「チケット」は GitHub の Issue、Azure DevOps の作業アイテムを指す。
レビューと修正は、指摘が尽きるかマージされるまで回る内側のループになる。

## 段の定義

| 段 | 入口条件 | 工程スキル | 成果物 | 人間の承認点 |
| --- | --- | --- | --- | --- |
| 設計 | 解決したいことはあるが、受け入れ条件の埋まったチケットが無い | `issue-design` | 受け入れ条件まで埋まったチケット | 方針の選択。委ねられた範囲外の仕様への回答。本文の承認 |
| 実装 | 受け入れ条件の埋まったチケットがあり、プルリクエストが無い | `issue-implement` | チケットに紐づくプルリクエスト | 着手の承認。受け入れ条件の不足を埋める回答 |
| レビュー | プルリクエストがあり、依頼者が見る側 | `pr-review` | 優先度付きの指摘と判定 | `[needs-human]` の判断 |
| 修正 | 未解決の指摘があり、依頼者が直す側 | `pr-fix` | 同じブランチへの push と対応報告 | 判断保留への回答。指摘の解決判定 |

工程スキルは 1 段 1 スキルで、GitHub と Azure DevOps で同じ本文を使う。基盤ごとに違う
操作は能力層 (GitHub は `github-ops`、Azure DevOps は `azure-devops`) が持ち、能力層は
段を持たない。どの段からも使う。

どの段からも呼ばれる支援工程がある。支援工程は成果物を先へ渡さず、呼んだ段に戻る。

| 支援工程 | 入口条件 | 成果物 |
| --- | --- | --- |
| 調査 | 決めるために調べることがある | チケットへの報告 |
| 分解 | 1 本のプルリクエストに収まらないチケットがある | 子チケット群 (着手の承認は子ごと) |
| ビルド調査 | ビルドが失敗している | 失敗ステップと原因の特定 |

## 実行基盤ごとの対応

| 段 | GitHub (ai-workflows) | Azure DevOps (azure-devops-skills) |
| --- | --- | --- |
| 設計 | `type:idea` + `ai:go` → ai-design | チャットで依頼 |
| 実装 | `type:feature` / `type:bug` + `ai:go` → ai-implement | チャットで依頼 |
| レビュー | PR オープン・push → ai-review | チャットで依頼 |
| 修正 | `ai:fix` (または `ai:auto` の自動付与) → ai-fix | チャットで依頼 |
| 調査 | `type:research` + `ai:go` → ai-research | `azure-devops` の `references/workflows/research.md` |
| 分解 | `type:epic` + `ai:go` → ai-plan | 設計の段でフィーチャーと子ストーリーに分割する |
| ビルド調査 | (対応なし) | `azure-devops` の「ビルド」 |

GitHub でも、手元の Claude Code・GitHub Copilot から工程スキルを直接呼べる。そのときの
進め方はチャットの列と同じになる。

承認の表し方は基盤ごとに違う。

| 承認 | GitHub (Actions) | チャット (Azure DevOps・手元の実行) |
| --- | --- | --- |
| 着手 | 人間が `ai:go` を付ける | 人間がチャットで依頼する |
| 成果物の発行 (起票・PR 作成) | 着手の承認に含まれる。発行物は可逆で、次の段へは人間のラベルでしか進まない | 本文を示してチャットで承認を得てから発行する |
| 人間の判断待ち | `ai:needs-human` を付けて停止する | チャットで質問して停止する |

GitHub Actions で発行の承認を着手の承認に含めてよいのは、発行された Issue・PR が
次の段を自動で起動しないため。チャットでプルリクエストの作成に承認を挟むのは、作成が
レビュアーへの通知を伴い、エージェントから取り消せないため。各段の手順が定める報告・
指摘のコメントは、その段の依頼自体が合意なので承認の対象外。

## 人間が握る制御点

段の中の進め方はエージェントの裁量で、次の線は越えない。いずれも取り消しが利かないか、
仕様の確定を伴う。エージェントの誤りは差分なら巻き戻せるが、これらは巻き戻せない。

- 仕様の穴を埋めない。受け入れ条件の不足と判断保留は、人間に返して止まる
- プルリクエストの承認 (approve・投票)・マージ (完了)・破棄をしない。マージの判断は人間
- 指摘スレッドを解決済みにしない。解消の判定は指摘した側
- 次の段の起動を代行しない (`ai:go` を付けない。チケットの状態 (`System.State` など) を
  進めない)。工程の進捗を宣言するのは人間と組織の運用
- ターゲットブランチへ直接 push しない。push 済みのコミットを force push で書き換えない

各工程スキルの「やらないこと」とワークフローの「禁止事項」は、この一覧をその段に展開した
もの。食い違ったら、この一覧に合わせて段の側を直す。

## 今どの段かの判定

依頼が段を名指ししないときは、成果物の有無で決める。上から順に判定する。

1. 受け入れ条件の埋まったチケットが無い → **設計**
2. チケットはあるが、紐づくプルリクエストが無い → **実装**
3. プルリクエストがある → 依頼者の立場で決まる。見る側なら**レビュー**、直す側なら
   **修正**。この 2 つは成果物では区別できない

判定の前に、依頼の中の識別子をチケットやプルリクエストに引き当てる。数字だけの名前を持つ
ファイル (`2251.md` など) や裸の数字はチケット番号であることがあるので、能力層で確認して
から段を決める。引き当てずに判定すると、ループの外の作業として扱ってしまう。

## この定義の使い方

- 段を足す・変えるときは、先にこの定義の表を更新する。表に現れない段は存在しない
- 段の手順は段ごとの工程スキルが持つ。GitHub のワークフローはその本文を埋め込んで
  実行時に読ませ (ai-workflows の `scripts/embed-skills.py`)、実行文脈に固有の指示
  (ラベル操作・止まり方) だけを prompt に書く
- 工程スキルは、自分の入口条件と隣の段への振り分けを冒頭に持つ。この定義と食い違ったら、
  この定義に合わせて直す
- 工程スキルは基盤固有の操作を本文に書かず、操作名で能力層を引く (契約は ai-workflows の
  `docs/platform-ops.md`)
