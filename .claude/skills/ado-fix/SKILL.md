# 修正 — レビュー指摘に対応する

プルリクエストに付いた指摘を読み、同じブランチに修正を push し、対応内容を報告するまでの
手順。

## この段の入口

入口条件: **未解決の指摘があり、依頼者が直す側**（ループの定義は
`../azure-devops/references/loop.md`）。条件が違う依頼は該当する段に渡す。

- レビューする側 → `ado-review`
- プルリクエストがまだ無い → 実装は `ado-implement`、設計は `ado-design`

## 能力層

Azure DevOps の操作（`pr …`）はすべて兄弟スキル `azure-devops` の `scripts/ado.py` を
通す。コマンドの一覧は `../azure-devops/SKILL.md`。兄弟配置（同じ skills ディレクトリ
直下）が前提。checkout・diff・commit・push は `git` CLI を使う。コミットメッセージの
規約は `../azure-devops/references/git.md`。

## 出力規約

書き方は `../azure-devops/references/writing.md`。この手順固有の上限は次の 2 つ。

- 報告コメントは合計 20 行以内。読み手が見るのは「指摘が捌けたか」「まだ自分が決めることが
  残っているか」の 2 点だけ
- 何をどう直したかは差分にある。文章で言い換えない

## 手順

### 1. 対象を特定する

```
pr get <id> --repo <repo>
```

`sourceRefName` / `targetRefName`（`refs/heads/` を外したもの）を控え、ソースブランチを
最新にして checkout する。

```
git fetch origin
git checkout <ソース> && git pull
```

### 2. 指摘と人間のコメントを読む

```
pr threads <id> --repo <repo> --unresolved-only
```

対応方針に迷ったら `--unresolved-only` を外して全体を読む。解決済みのスレッドに人間の判断が
残っていることがある。

### 3. 差分を把握する

```
git diff origin/<ターゲット>...origin/<ソース>
```

何が変更済みかを知らずに指摘だけ読むと、既に直っているものを直す。

### 4. 指摘を分類する

| 分類 | 条件 | 扱い |
| --- | --- | --- |
| 対応する | 妥当な指摘 | 直す |
| 対応しない | 人間が「対応不要」「仕様どおり」と明示している | 触らない |
| 判断保留 | 仕様の判断が要り、正解が一意に決まらない | 直さず、決めてほしいこととして出す |

**人間のコメントが常に最優先。** レビューの指摘と人間のコメントが食い違ったら人間に従う。

迷ったら「判断保留」に倒す。独断で埋めた仕様は差分の中に紛れ、次のレビューでも仕様の誤りとして
は現れない。

### 5. 優先度の高いものから直す

P0 → P1 → P2 の順に着手する。途中で打ち切られても P0 が片付いている状態にするため、順序を
崩さない。

指摘に修正案があれば、推奨として示された案を第一候補にする。代案を採る場合、どれも採らない
場合は、その理由を報告に 1 行書く。

誤動作の指摘（P0 / P1 相当）は、直す前にその誤動作で落ちるテストを 1 本足し、実行して落ちる
ことを確認する。足さなくてよいのは次の 2 つだけ。

- 誤動作ではない指摘（書式・命名・重複など）— 直す前に落ちるテストが書けない。分類名では
  なく指摘の中身で決める。条件を挙げて誤りを述べている指摘は、分類が「重複」でも誤動作
- リポジトリにテストの実行コマンドが無い（CI 設定・パッケージのスクリプト定義・テストランナー
  の設定のいずれにも無い）。基盤の新設はしない。この理由で足さなかったときは報告の末尾に
  1 行書く

判定はリポジトリ単位。対象のコンポーネント・ファイルに既存のテストが無いことは足さない理由に
ならない。テストファイルを新しく作るのは基盤の新設ではない。足すのは誤動作を再現する 1 本に
とどめ、周辺の未テスト箇所には広げない。

指摘と無関係な改善はしない。気づいた点は報告の末尾に 1 行で残す。

### 6. テストを通す

5 で足したテストと既存のテストを実行して通す。どちらも無いなら飛ばす。5 の 2 つに当たらない
誤動作の指摘で、落ちるテストを足していないものがあれば手順 5 に戻る。テストを通すために
テスト自体を書き換えない。実装を直せないなら「判断保留」に回す。

### 7. 同じブランチに push する

```
git commit …
git push origin HEAD
```

コミットメッセージの書式は `../azure-devops/references/git.md`。指摘対応であることは
type にしない。直した内容で type を決める。

新しいブランチを作らない。force push しない。ターゲットブランチへ直接 push しない。

### 8. 報告する

```
pr comment <id> --repo <repo> --text @report.md
```

```
| 指摘 | 対応 |
|---|---|
| src/a.ts:42 の 0 除算 | 修正（ガード追加） |
| 命名の統一 | 見送り — 人間が対応不要と判断済み |

**決めてほしいこと**
1. 〜を A / B どちらにするか（A: …、B: …）
```

- 表は 1 指摘 1 行。対応欄は「修正」か「見送り — 理由 1 句」だけ。直し方は書かない
- 「決めてほしいこと」は判断保留があるときだけ。1 件 1 行で選択肢と帰結を並べ、推奨は
  付けない。決めるのは人間
- スレッドを解決済みにしない。指摘が解消したかを判断するのは指摘した側

判断保留が 1 件でもあるなら、報告したところで止める。回答を待たずに次へ進まない。

## やらないこと

- 指摘と無関係な変更・リファクタリング・新機能の追加
- 新しいブランチの作成、force push、ターゲットブランチへの push
- プルリクエストの完了・破棄・投票
- 人間が「対応不要」と判断した指摘への対応
- テストを通すためのテスト自体の書き換え
