# レビュー — PR をレビューする

PR をレビューし、指摘を投稿するまでの手順。コードは変更しない。GitHub でも
Azure DevOps でも同じ手順で動く。

## この工程の入口

入口条件: **PR があり、依頼者が見る側** (ループの定義は中央リポジトリ ai-workflows の
`docs/loop.md`)。条件が違う依頼は該当する工程に渡す。

- 指摘に対応して直す側 → `pr-fix`
- PR がまだ無い → 実装は `issue-implement`、設計は `issue-design`

## 能力層

基盤ごとに違う操作は、この本文に「紐づくチケットを読む」のような**操作名**で書いてある。
実行方法は能力層のスキルが持つ。

| 基盤 | 判定 | 能力層 |
| --- | --- | --- |
| GitHub | `git remote get-url origin` が `github.com` を指す | `github-ops` |
| Azure DevOps | それ以外 (Azure DevOps Server、`dev.azure.com`) | `azure-devops` |

用語も能力層に合わせて読み替える。**チケット**は GitHub の Issue、Azure DevOps の
作業アイテム。**受け入れ条件**は Azure DevOps では受け入れ基準のフィールドにある。
差分は `git` CLI で取る。

## 実行文脈による違い

| | チャット (Claude Code / GitHub Copilot) | GitHub Actions |
| --- | --- | --- |
| 投稿の形 | 行を名指しできる P0 / P1 / `[needs-human]` は「PR の行にコメントする」で行に置き、判定・P2 の表・決めてほしいことをトップレベルの 1 コメントにまとめる | 全体をトップレベルの 1 コメントにまとめる。ワークフローがその判定を読んで次を決める |
| 指摘件数の上限 | 既定の 3 件 | ワークフローの指定に従う |

PR の状態 (GitHub のラベル `ai:fix` / `ai:needs-human` など) は、GitHub Actions の
ワークフローが指示したときだけ動かす。チャットからの実行では触らない。

## 出力規約

`output-contract` スキルを前提とする。ここで定めるのは、レビュー固有の優先度・書式・上限。

- 判定を最初の 3 行に置く。折りたたみの外は **合計 30 行以内**
- **1 件 1 件が読んだだけで意味の通る指摘であること。**「どの機能・画面の話か」
  「どんな条件で起きるか」「誰がどう困るか」が欠けた指摘は、短くても読み手にコードを
  読み直させるので削減にならない。件数を削って 1 件の密度を上げる。逆はしない
- 畳んでよいのは調査の経緯とコード引用だけ。**発生条件と影響は指摘の本体**なので
  `<details>` に入れず本文に書く

### 分類

| 分類 | 意味 |
| --- | --- |
| `[auto]` | 正解が一意に決まる修正。明確なバグ、エッジケース漏れ、規約違反、秘密情報の混入など |
| `[needs-human]` | 紐づくチケットの思想・受け入れ条件からの乖離、未定義の仕様、トレードオフを伴う設計判断など、人間が決めるもの |

**分類に迷ったら必ず `[needs-human]` に倒す。**

### 優先度

| 優先度 | 意味 |
| --- | --- |
| P0 | このままマージすると壊れる・危険。クラッシュ、データ破損、セキュリティホール、秘密情報の混入、受け入れ条件の未達 |
| P1 | 特定条件で誤動作する。エッジケース漏れ、規約違反、エラーハンドリングの欠落 |
| P2 | 動作は正しいが保守性・可読性に影響する。重複、分かりにくい分岐 |

迷ったら低い方に倒す。P0 を安売りすると優先度が機能しなくなる。
判定は優先度から機械的に決まる (P0/P1 あり → `❌ 要修正`、P2 のみ → `⚠️ 軽微`、
ゼロ → `✅ 問題なし`)。

### 件数

- 本文に出すのは **P0 → P1 → P2 の順で上位 3 件**まで (実行側が上限を指定したらそれに
  従う)。件数ではなく優先度で切る。P0 が枠を超えるなら P1 以下は 1 件も出さない
- ただし **`[needs-human]` は上限の対象外で全件出す。** 人間の意思決定に必要で、上限で
  消えると止まる理由が伝わらない
- 溢れた分は最後に `- その他 P2 N 件` の 1 行だけで示す。内訳は書かない
- スタイル・nit・命名の好み・「〜した方が良いかも」は指摘しない。linter / formatter の
  領域で、人間の時間を使う価値がない

## 手順

### 1. 対象と既出のコメントを読む

「PR を読む」でソースブランチ・ターゲットブランチと最新コミットを控える。最新コミットは
手順 7 で、レビュー中に push が入っていないかの確認に使う。

「PR の指摘を読む」で、トップレベルと行の両方のコメントを読む。他のレビュアー
(人間・他のボット) が指摘済みの内容を重ねて書かない。

### 2. 差分と規約を読む

```
git fetch origin
git diff origin/<ターゲット>...origin/<ソース>
```

3 点の `...` はマージベース以降のソース側の変更だけを出す。作業対象リポジトリの clone が
手元に無いなら用意する。置き場所が分からなければ依頼者に 1 行で聞く。どちらもできない
なら、レビューを行わずにその理由を報告して止まる。変更ファイルの一覧だけでレビューを
書かない。行を名指しできない指摘は調査コストが人間側に移るだけで、優先度も付けられない。

リポジトリの `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` があれば読み、
規約への準拠を確認する。

### 3. 観点

- バグ・ロジックエラー・エッジケースの見落とし
- セキュリティ (入力検証、認証認可、秘密情報の混入)
- 紐づくチケットの受け入れ条件を満たしているか (手順 4)
- プロジェクト規約との整合性

### 4. 受け入れ条件をテストと突き合わせる

「紐づくチケットを読む」で受け入れ条件を読み、受け入れ条件 1 件ごとに、それを検証して
いるテストが差分か既存コードにあるかを見る。差分だけでは「動くか」しか見られず、
「求められたものか」は判断できない。

PR 本文に「受け入れ条件と検証」の表があれば、その各行から始める。

- 行の対応 — 表の行がチケットの受け入れ条件と 1 対 1 に対応していないなら P1。欠けた
  条件、統合された条件、条件に無い行、原文から条件を特定できない言い換えが当たる。行の対応が
  崩れていると、以下の突き合わせが何を検証したことにもならない
- OK の行 — 名指しされたテストが差分か既存コードにあり、アサーションが条件の文言を
  検証しているかを読む。常に通るアサーション、実装の出力を写しただけの期待値は検証に
  なっていない。その行は未検証として扱い、条件の充足を差分から判断し直す
- 未検証の行 — skip 理由 (手動のみ / 対象外 / 外部依存) が差分と矛盾しないかを見る。
  実装後なら書けるはずのテストが skip のままなら P1。区分の 1 語だけで具体的な理由が無い、
  または対応する手動確認手順に準備・操作・確認のどれかが欠けているなら P1。一時的なコード
  変更で起こせる状態を手動確認に回しているなら、テストの中で起こせないかを修正案にする

紐づくチケットが無いときは、PR 本文に書かれた目的と差分を突き合わせ、チケットが紐づいて
いないこと自体は指摘にしない。表が無いときは、受け入れ条件の各件を自分で差分と突き合わせる。検証しているテストが無く、
自動テストできない理由も書かれていない条件は P1。表の不在そのものは指摘にしない。

### 5. 到達条件を確認してから書く

指摘を書く前に、その箇所へ到達する条件を確認する。変更された関数・コンポーネントの
参照元を、呼び出し側が特定できるまで辿り、どの画面・機能から / どんな状態のときに
実行されるかを押さえる。呼び出し側がコード上に存在しないこともあるので、見つからないと
判断した時点で打ち切る。これをやらないと影響欄を埋められない。

取り下げてよいのは、**呼び出し側を特定した上で、そこでガードされていると確認できた**
指摘だけ。**参照元 0 件は到達しない根拠にならない** (新規 export で配線が後続 PR、
ファイルベースルーティング、文字列キーの dispatch、DI、ライブラリの公開 API は 0 件で
出る)。確認できないときは取り下げず、影響欄を省いて指摘を残す。

### 6. 再レビューのとき

同じ PR を 2 回目以降にレビューするときは、発散を防ぐため次に限る。

- 前回の指摘が解消されたかの確認と、修正で新たに混入した問題の検出だけを行う。新規の
  軽微な指摘 (スタイル、nit) は追加しない
- 人間または修正担当が「対応不要」と判断済みの項目を蒸し返さない

### 7. 投稿する

投稿の直前に「PR を読む」で最新コミットを読み直し、手順 1 で控えたものと一致するかを
確かめる。一致しなければレビュー中に push が入っており、行番号がずれている。手順 2 から
やり直す。

「実行文脈による違い」の表の形で、「PR にコメントする」(と「PR の行にコメントする」) で
投稿する。トップレベルのコメントは次の形式を厳守し、これ以外は書かない。行に置いた指摘は、
トップレベルでは見出し行だけを残し、ブロックの本体は行コメントに書く。

```
**判定**: ❌ 要修正 (P0 1 / P1 1 / P2 5、うち [needs-human] 1)

### P0 [auto] 休暇プランナーの候補一覧 — src/lib/plan.ts:47
- **現象**: 残日数が 0 の状態で開くと、候補が 1 件も無いまま
  「実行できる案」の見出しだけが表示される
- **影響**: 残日数を使い切った利用者に、選べる案があるように見える
- **修正案**: 推奨 A — 残 0 のときは専用の空状態を出す
  (理由: 候補ゼロという事実と見出しが一致する) / B: 見出しの文言だけ変える

### P1 [needs-human] 予算判定 — src/lib/budget.ts:88
- **現象**: 下書き中の申請を残日数から引くため、保存前に残 0 と判定される
- **影響**: 保存していない利用者が「残っていません」と案内される
- **修正案**: A: 現状維持 (下書きに追従する) / B: 保存済みの値で判定する
  (追従しなくなるが、保存前の誤案内は消える)

**P2**
| 箇所 | 指摘 | 修正案 |
|---|---|---|
| src/lib/plan.ts:56 | 手動運用では接続詞の指す先が無い文になる | 接続詞を落とす |

- その他 P2 4 件

**決めてほしいこと**
1. 〜を A/B どちらにするか (A: …、B: …)
```

- 括弧内の件数は上限で切る前の**検出した全件**を書く。何件が本文に出ていないかが
  分かるようにするため
- **P0 / P1 / `[needs-human]` は 1 件ずつブロックで書く。** 見出し行は
  `### 優先度 分類 機能・画面名 — path:line`。機能・画面名は、その箇所が何をしている
  場所かをコードやチケットから確認して 15 字以内で書く (ファイル名の言い換えにしない)
  - **現象** — どんな条件で何が起きるかを 1〜2 文 (120 字以内)。「いつ」が分かること。
    診断名ではなく観測できる事象を書く
  - **影響** — 誰がどう困るかを 1 文 (60 字以内)。確認できないときはこの行ごと省く
  - **修正案** — 必須。`推奨 A — <何をするか> (理由: <1 句>)` の形で推奨を 1 つ明示し、
    代案があれば ` / B: <何をするか>` を続ける。ただし **`[needs-human]` には推奨を
    付けない。** 決めるのは人間なので、`A: <案> (帰結) / B: <案> (帰結)` と並べるだけに
    する。コードは書かない
  - 1 ブロックは 6 行以内。超えるなら現象か修正案を削る
- **P2 は 1 件 1 行の表**にまとめる (`箇所 / 指摘 / 修正案`)。P2 が無ければ表ごと省く
- 30 行を超えるなら `[auto]` の件数を減らす。`[needs-human]` を落として行数を守っては
  いけない。両立できないときは `[needs-human]` を全件残し、30 行を超えてよい。調査の
  経緯とコード引用だけ `<details>` に畳んでよい (最大 3 件、各 5 行以内)
- 「決めてほしいこと」は `[needs-human]` があるときだけ。1 件 1 行で、選択肢とそれぞれの
  帰結を示す。人間はここだけ読めば判断できること
- 指摘がゼロなら `**判定**: ✅ 問題なし` の 1 行だけを投稿する

## やらないこと

- ファイルの作成・編集
- PR の承認 (approve・投票)・マージ (完了)・破棄 (マージの判断は人間)
- レビュースレッドの解決済み化 (解消の判定は指摘した側)
- 指摘の修正の代行 (直す側は `pr-fix`)
- 出力規約に列挙していないセクションの追加
