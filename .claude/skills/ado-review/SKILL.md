# レビュー — プルリクエストをレビューする

Azure DevOps 上のプルリクエストをレビューし、指摘を投稿するまでの手順。

## この段の入口

入口条件: **プルリクエストがあり、依頼者が見る側**（ループの定義は
`../azure-devops/references/loop.md`）。条件が違う依頼は該当する段に渡す。

- 指摘に対応して直す側 → `ado-fix`
- プルリクエストがまだ無い → 実装は `ado-implement`、設計は `ado-design`

## 能力層

Azure DevOps の操作（`wit …` / `pr …`）はすべて兄弟スキル `azure-devops` の
`scripts/ado.py` を通す。コマンドの一覧は `../azure-devops/SKILL.md`、WIQL やフィールドの
扱いは `../azure-devops/references/recipes.md`。兄弟配置（同じ skills ディレクトリ直下）が
前提。差分の取得はローカル clone に対する `git` CLI で行う（手順 2）。

## 出力規約

書き方の原則と投稿先ごとの制約は `../azure-devops/references/writing.md` にある。
ここで定めるのは、レビュー固有の優先度・書式・上限だけ。

### 優先度

| 優先度 | 意味 |
| --- | --- |
| P0 | このままマージすると壊れる・危険。クラッシュ、データ破損、セキュリティホール、秘密情報の混入、受け入れ基準の未達 |
| P1 | 特定条件で誤動作する。エッジケース漏れ、規約違反、エラーハンドリングの欠落 |
| P2 | 動作は正しいが保守性に影響する。重複、分かりにくい分岐 |

迷ったら低い方に倒す。P0 を安売りすると優先度が機能しなくなる。
判定は優先度から機械的に決まる（P0/P1 あり → ❌、P2 のみ → ⚠️、ゼロ → ✅）。

### 指摘の書式

P0 / P1 / `[needs-human]` はブロックで書く。読み手がコードを開き直さずに判断できることが
条件で、そこを削ると調査コストが人間側に移るだけになる。

| 欄 | 内容 | 上限 |
| --- | --- | --- |
| 見出し | `優先度 分類 機能・画面名 — path:line`。どこの何の話かを名指しする | 機能名 15 字 |
| 現象 | どんな条件で何が起きるか。診断名ではなく観測できる事象 | 1〜2 文 / 120 字 |
| 影響 | 誰がどう困るか。確認できないときは行ごと省く | 1 文 / 60 字 |
| 修正案 | `推奨 A — 何をするか (理由: 1 句)`。代案は ` / B: …` で続ける | — |

1 ブロック 6 行以内、本文は合計 30 行以内。P2 は 1 件 1 行の表にまとめる。
本文に出す指摘は既定 3 件まで（P0 → P1 → P2 の順に詰め、溢れた分は 1 行に集約）。
人間の判断が要る指摘は `[needs-human]` を付け、推奨を付けずに選択肢と帰結だけを並べる。
これは件数・行数の上限の対象外で、減らしたり畳んだりしない。

## 手順

### 1. 対象を特定する

```
pr get <id> --repo <repo>
```

`sourceRefName` / `targetRefName`（`refs/heads/` を外したもの）と
`lastMergeSourceCommit` を控える。最後のものは 5 で行アンカーの検証に使う。

### 2. 差分を取る

差分は REST では取得しない。Azure DevOps Server の REST が返すのは変更されたファイルの
一覧までで、行単位のパッチは返らない。対象リポジトリのローカル clone で `git` を使う。

```
git fetch origin
git diff origin/<ターゲット>...origin/<ソース>
```

3 点の `...` はマージベース以降のソース側の変更だけを出す。

ローカル clone が無いなら用意する。置き場所が分からなければ依頼者に 1 行で聞く。どちらも
できないなら、レビューを行わずにその理由を報告して止まる。REST で取れる変更ファイルの一覧
だけでレビューを書かない。行を名指しできない指摘は調査コストが人間側に移るだけで、優先度も
付けられない。

### 3. 満たすべき条件を読む

```
pr workitems <id> --repo <repo>
```

紐づく作業アイテムがフィールドごと返る。受け入れ基準
（`Microsoft.VSTS.Common.AcceptanceCriteria`）と実装を突き合わせる。
差分だけでは「動くか」しか見られず、「求められたものか」は判断できない。

受け入れ基準 1 件ごとに、それを検証しているテストが差分か既存コードにあるかを見る。この
突き合わせは説明の書式に関わらず行う。

説明に受け入れ基準と検証の表があれば、その各行から始める。

- OK の行 — 名指しされたテストが差分か既存コードにあり、アサーションが基準の文言を
  検証しているかを読む。常に通るアサーション、実装の出力を写しただけの期待値は検証に
  なっていない。その行は未検証として扱い、基準の充足を差分から判断し直す
- 未検証の行 — skip 理由（手動のみ / 対象外 / 外部依存）が差分と矛盾しないかを見る。
  実装後なら書けるはずのテストが skip のままなら P1

表が無いリポジトリもある（PR テンプレートに検証欄が無ければ実装の段は作らない）。そのときは
受け入れ基準の各件を自分で差分と突き合わせる。検証しているテストが無く、自動テストできない
理由も書かれていない基準は P1。表の不在そのものは指摘にしない。

### 4. 既出の指摘を読む

```
pr threads <id> --repo <repo> --unresolved-only
```

他のレビュアーが指摘済みの内容を重ねて投稿しない。

### 5. 影響を確認してから書く

影響欄を埋めるため、指摘を書く前にその箇所へ到達する条件を確認する。変更箇所の参照元を、
呼び出し側が特定できるまで辿る。呼び出し側がコード上に存在しないこともあるので、
見つからないと判断した時点で打ち切る。

取り下げてよいのは、呼び出し側を特定してガードを確認できた指摘だけ。**参照元 0 件は
到達しない根拠にならない**（新規 export、ファイルベースルーティング、文字列キーの
dispatch、DI、公開 API はいずれも 0 件で出る）。確認できないときは取り下げず、影響欄を
省いて指摘を残す。

### 6. 投稿する

行を名指しする指摘はインラインスレッドに、設計や全体構成に関わる指摘はトップレベルの
スレッドに書く。

```
pr comment <id> --repo <repo> --file <パス> --line <N> --text "…"   # インライン
pr comment <id> --repo <repo> --text @review.md                      # トップレベル
```

投稿の直前に、1 で控えた `lastMergeSourceCommit` が
`git rev-parse origin/<ソース>` と一致するか確認する。一致しなければレビュー中に新しい
push が入っており、行番号がずれている。2 からやり直す。

気づいたことをすべて行コメントにすると、本当に直すべき箇所が埋もれる。
インラインコメントは名指しできる箇所に限る。

## やらないこと

- プルリクエストの完了・破棄・投票（マージの判断は人間）
- 指摘スレッドの解決済み化（解消の判定は指摘した側）
- 指摘の修正の代行（直す側は `ado-fix`）
